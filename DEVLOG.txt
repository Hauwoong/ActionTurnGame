### 오늘 한 것

- 주사위(DiceData) 기반 카드 효과 처리 구조 설계
- 카드 → 주사위 → 전투 처리 흐름 설계

- BattleContext 기반 전투 정보 전달 구조 설계
- CardUI ↔ BattleManager ↔ CardData 연동 구조 개선
- 카드 효과 처리 로직 설계 및 테스트

### 문제
- CardData 추상 클래스와 virtual / abstract 혼용으로 컴파일 오류 발생
- BattleContext 전달 구조 설계 미흡으로 UseCard 호출 오류 발생
- CardData.Use / Resolve 구조 혼란으로 인한 타입 불일치 오류

### 해결
- CardData 구조를 추상 기반 공통 처리 + 데이터 중심 구조로 재설계
- 카드 사용 시 BattleContext를 통해 전투 정보 전달하도록 구조 수정
- 카드 타입 분류(enum) 제거 → 주사위 데이터 중심 구조로 통합
- 기본 카드와 특수 카드 상속 구조 방향 정립
- 카드 역할을 주사위 조합으로 표현하는 방식 확정

### 배운 점
- 카드 시스템의 핵심은 “카드 타입”이 아니라 “행동 데이터”이다
- ScriptableObject + 데이터 중심 구조는 확장성이 매우 높다
- abstract / virtual은 역할이 명확할 때만 사용하는 것이 좋다
- BattleContext 같은 컨텍스트 객체는 시스템 결합도를 낮춰준다
- 중복 구조를 의심하고 제거하는 설계가 장기 유지보수에 중요하다

### 문제 — 중요한 실수 기록

■ "참조 0건"을 "지워도 되는 코드"로 착각
- Bout.cs 는 어디서도 참조되지 않았지만 "개념이 살아있다"는 이유로 존치 결정

- 컴파일 실패 상태의 Unity 는 Add Component 를 거부 → "컴포넌트가 안 붙는다"는 증상으로 나타남
- 참조 수와 컴파일 가능 여부는 별개다

■ IRng.Range 의 경계 규약이 문서화되지 않음
- DeterministicRng.Range 는 random.Next(min, max + 1) → max 포함
- Unity 의 Random.Range(int, int) 는 max 제외 → 그 관습을 아는 사람일수록 착각
- CardZone.Shuffle 이 rng.Range(0, i + 1) 로 작성됨 → ArgumentOutOfRangeException
- 덱이 비었을 땐 루프가 안 돌아 드러나지 않다가, 카드를 넣는 순간 터짐
- 주사위/속도 호출부는 포함 기준이 맞아 정상 동작 → 셔플만 틀린 채로 잠복해 있었음

■ using UnityEngine 이 없어도 Unity 에 종속될 수 있음
- BattleSnapShot 은 using UnityEngine 이 없는데 IEnumerable<Character> 를 받고 있었음
- Character 는 MonoBehaviour → 타입 참조만으로 종속
- 계층 순수성은 using 목록이 아니라 시그니처에 등장하는 타입으로 판단해야 함

■ Editor.log 는 누적된다
- 이미 삭제된 파일의 과거 에러가 그대로 남아 있음
- error CS 를 grep 할 때 해당 파일/멤버가 현재도 존재하는지 교차 확인 필요

■ 호출자 없는 코드가 대량으로 방치돼 있었음
- CreateBattle / StartTurn / ExecuteCombat / EndBattle 모두 호출자 0
- EndTurn 만 TurnUI 버튼에 연결돼 있었고, 그마저 ExecuteCombat 을 부르지 않아
  등록한 액션이 해석 없이 BoutGraph.Clear() 로 버려지고 있었음
- 컴파일이 되는 것과 실행 경로가 이어진 것은 별개다

■ 진영 개념 부재
- BattleSnapShot 이 양 진영을 평평한 리스트 하나로 합쳐 받아 팀 정보가 소실
- IsBattleOver() 가 전체 생존자 수만 세어 사실상 "최후의 1인" 규칙이 됨
- 3v3 에서 한 팀이 전멸해도 전투가 끝나지 않는 상태였음

### 해결
- Bout.cs / BoutCandidate.cs 삭제, LorRuleSet 계열 삭제
- enum Team 도입, IsBattleOver() → TryGetBattleResult(out Team? winner) 로 교체
- BattleStarter 신설, EndTurn 이 턴 진행 순서(전투 해석 → 종료 판정 → 다음 턴)를 소유
- BattleManager 가 Character → CharacterData 추출을 담당, BattleSnapShot 은 순수 데이터만 수신
- 추출은 즉시 평가. 지연 평가(LINQ Select)로 넘기면 멤버 접근이 다시 엔진 안에서 일어남
- CardZone.Shuffle 은 rng.Range(0, i) 로 수정. IRng.Range 는 이름/주석으로 규약 명시 검토 중

### 배운 점
- 데드 코드는 "안 쓰인다"와 "컴파일된다"를 따로 확인해야 한다
- 난수 API 는 경계 규약을 이름이나 주석에 드러내야 한다. Range 라는 이름은 Unity 관습 때문에 오해를 부른다
- 계층 순수성은 using 이 아니라 시그니처로 판단한다
- 인스펙터 필드는 타입에 따라 넣을 것이 다르다 — Character 는 씬 오브젝트, CharacterData 는 에셋
- 잘못된 세팅은 NullReferenceException 이 아니라 위치(진영/인덱스/이름)를 담은 메시지로 드러나야 원인 추적이 빠르다
- 버그가 "지금까지 안 터진 것"이 "정상이었다"는 뜻은 아니다. 조건이 안 맞아 잠복했을 뿐일 수 있다

## 2026-07-22 — 데미지가 HP UI 에 반영되지 않던 문제 (이벤트 실행 순서)

합은 잡히는데 HP 텍스트가 계속 50 → 원인을 파이프라인 끝에서 끝까지 추적한 기록.

### 문제점

■ 주사위를 캐릭터 큐에 싣는 단계가 파이프라인에서 통째로 빠져 있었음
- 카드 등록(ActionRegisteredEvent → BoutGraph)은 되는데, 그 카드의 주사위를 싣는 CharacterRuntime.UseAction 호출자가 0 건
- 그래서 ResolveCombat 이 PeekDice == null 로 즉시 탈출 → 데미지 0, 카드도 슬롯에 잔류
- 클래시 자체가 아니라 "합은 걸리는데 데미지가 안 나오는" 증상으로 나타남

■ 데미지는 실제로 들어가는데 HP 텍스트만 50 에서 안 변함 (이번 기록의 핵심)
- 임시 로그로 확인: [Damage] target=0 amount=1 이 찍히고, 스택도 DamageEvent → AddLog → HpUI.OnDamage 까지 정상 도달
- 즉 모델 HP 는 깎이고 있는데 화면만 stale

■ 3턴이 지나면 데미지가 더 이상 안 들어감
- 에너지(빛)가 소비만 되고 회복이 없음. maxEnergy 3, cost 1 → 3턴이면 0
- 등록은 에너지를 검사하지 않고 UseAction(해석 시점)만 검사 → 합은 걸리는데 조용히 데미지 0

■ (부수 발견) BoutGraph.Clear() 가 actionBySlot 을 안 지움
- edges/targetMap/interceptCandidates 만 clear → 턴이 넘어가도 슬롯에 카드 이름이 남음

### 고민

■ HP 텍스트가 안 변하는 진짜 원인
- AddLog 은 동기다. 그 한 줄이 Dispatch → HpUI.OnDamage → Refresh 까지 그 자리에서 다 실행하고 리턴한다
- Refresh 는 cr.CurrentHp 를 그 순간 다시 읽는다 → "언제 읽느냐"가 전부
- 고치기 전 DamageEvent 는 AddLog(로그) → TakeDamage(HP 감소) 순이었다
  → Refresh 가 아직 안 깎인 HP 를 읽어 그림. 모델은 그다음에야 깎임. UI 는 영원히 한 박자 전 값

■ "로그 먼저" vs "상태 먼저" — 어느 쪽이 규칙인가
- CLAUDE.md 규칙은 "AddLog → CharacterRuntime 호출" (로그 먼저)로 적혀 있었음
- 실제 코드를 세어보니 8 개 중 5 개는 이미 "상태 먼저"(EnergyUse/ChangeMaxHp/GainEmotionStack/Draw/Death)

### 배운 점

- 원작 재현 프로젝트에서는 "규칙이 뭐였는지" 자체가 검증 대상이다. 문서에 적힌 원작 규칙도 틀릴 수 있고,
  실제 플레이 경험이 있는 쪽이 교정해야 한다
- 새 상태 변경이 필요할 때 비슷한 자원(스태거)의 기존 메서드 패턴을 먼저 찾으면 설계가 빨라진다
- 로그의 수치는 "요청량"이 아니라 "실제 변화량"을 기록해야 로그만으로 상태를 재구성할 수 있다
- 이벤트를 enqueue 하는 쪽이 조건을 검사하는 구조(EmotionLevelUp 의 조기 리턴 가드)는
  enqueue 지점이 늘어나면 깨질 수 있는 암묵적 약속이다 — 지금은 문제없지만 기억해 둘 것

## 2026-07-22 — 일방 공격이 통째로 증발하던 버그 (CombatExecutor)

배경: 상대가 카드를 내지 않은 슬롯을 때리면 아무 일도 일어나지 않았다.
ResolveUnopposedDice 와 BoutStartEvent(action, null, ...) 경로는 진작 구현돼 있었는데
도달하는 코드가 없던 상태.

### 문제점

■ 타겟을 action 이 아니라 graph.edges 에서만 찾고 있었음
- RunQueue 의 `if (!graph.edges.TryGetValue(slot, out var targetSlot)) continue;`
- edge 는 BoutGraph.Connect 가 양방향으로만 만든다 = 양쪽이 서로를 겨냥해야 생긴다
- 즉 "합이 성립한 공격"만 처리되고, 합이 아닌 공격(일방)은 전부 continue 로 증발
- 덤으로 이 continue 는 visited.Add 도 하지 않는 유일한 탈출 경로였음

### 고민

■ "edge 없으면 폴백 targetSlot 만 구해서 기존 흐름에 태우면 되지 않나?" → 안 됨
- 내 타겟이 제3자를 노리는 액션을 갖고 있으면(edge 없음, ActionBySlot 에는 있음)
  기존 클래시 조건이 그걸 opponent 로 잡아 성립하지도 않은 합을 만들고,
  상대를 visited 처리해 상대의 진짜 합까지 날린다
- edge 없음 = 무조건 일방 경로. 클래시 조건에 hasEdge 를 명시해야 함

■ TryGetValue 실패 시 out 값의 함정
- SpeedSlot 은 struct → 실패 시 null 이 아니라 default = (characterId 0, slotIndex 0)
- 멀쩡해 보이는 값이라 그대로 흘리면 무조건 0번 캐릭터를 때린다
- 폴백은 반드시 action.TargetSlot 에서 가져와야 함 (이미 손에 든 action 에 붙어 있음 —
  ActionBySlot 재조회 불필요)

### 해결법

■ RunQueue 재구조화 (체크리스트 방식으로 구현)
1. bool hasEdge = graph.edges.TryGetValue(slot, out var targetSlot)
2. !hasEdge 면 targetSlot = action.TargetSlot 으로 대체
3. IsTargetAlive 검사는 공통 경로에서 통과
4. 클래시 조건에 hasEdge 추가 → edge 없으면 자동으로 else(일방)행
5. 모든 탈출 경로가 visited.Add(slot) 을 찍는 것 확인

■ 플레이 검증
- 빈 슬롯 공격 → 데미지 반영 확인
- 정상 합 회귀 없음, 다음 턴 정상 진행

### 배운 점

- struct 를 out 으로 받는 TryGetValue 는 실패해도 "그럴듯한 값"(default)을 돌려준다.
  참조 타입의 null 처럼 터져 주지 않으므로, 실패 분기를 안 만들면 조용히 엉뚱한 대상을 가리킨다
- "경로가 구현돼 있다"와 "경로에 도달한다"는 별개다. 일방 공격 처리 코드는 완성돼 있었지만
  호출부의 필터가 그 앞에서 전부 걸러내고 있었다
- 루프의 탈출 경로마다 불변식(여기선 visited 마킹)이 지켜지는지 경로별로 세어봐야 한다.
  한 경로만 빠뜨려도 "가끔 두 번 처리되는" 류의 버그가 된다

## 2026-07-22 — 클래시 데미지를 원작 규칙으로 교정 (DiceRuleTable)

배경: 승자 데미지가 rollA - rollB(차이)로 구현돼 있어 데미지가 1~3 으로 매우 작고
무승부면 0. 원작은 승자가 자기 굴림값 전체를 넣는다.

### 문제점

■ "차이" 공식이 테이블 전체에 깔려 있었음
- Attack/Counter 승리 데미지, 막기 승리 스태거, 회피 승리 회복 전부 차이 기반
- 원작 필과 크게 어긋나는 지점이라 결정 후 일괄 교정

### 고민

■ 전부 "전체"로 바꾸면 되는 게 아니었음 — 매치업별 예외가 있다
- Attack 이 Block 을 이기면: 데미지 = 공격값 - 수비값 (진 방어 주사위가 굴림값만큼 경감, 원작 규칙)
- 나머지(vs Attack/Evade/Counter 승리 데미지): 굴림값 전체
- 막기 승리 스태거: 경감 없이 전체 (사용자가 원작 지식으로 확정)
- 회피 승리 회복: 회피 굴림값 전체

■ 1차 수정에서 두 셀이 누락됨
- Block-vs-Attack 계열 두 셀(스태거)만 차이로 남아,
  같은 공격 타입인 Counter 상대 셀과 규칙이 어긋나는 비일관 상태가 됨
- 대칭 셀(A↔B)과 "같은 역할의 주사위 타입" 셀을 표로 대조해서 발견

### 해결법

- 승리 수치를 굴림값 전체로 통일, Attack/Counter vs Block 승리 데미지만 경감 유지
- ResolveUnopposedDice 는 원래 CurrentRoll 전체를 쓰고 있었으므로,
  이번 교정으로 합과 일방의 데미지 스케일이 일치하게 됨

### 배운 점

- 룰 테이블을 고칠 땐 "대칭 셀"과 "같은 역할 타입의 셀"을 표로 놓고 대조해야 누락이 보인다.
  16개 셀을 눈으로 훑는 것만으로는 두 셀 누락을 놓쳤다
- 에디터에서 고쳤다고 디스크에 반영된 것이 아니다 — 리뷰는 저장된 파일 기준으로 한다

## 2026-07-22 — BoutGraph.Clear 보완 + "데미지 로그 2번" 소동

### 문제점

■ BoutGraph.Clear() 가 actionBySlot 을 안 지움 (구 3번)
- edges / targetMap / interceptCandidates 만 비워서 턴이 넘어가도
  슬롯 디버그 UI 에 지난 턴 카드 이름이 잔류
- BuildQueue 가 actionBySlot.Values 를 돌므로 스테일 액션이 섞일 여지도 있었음

■ 수정 후 "데미지 로그가 2번씩" 나온다는 새 증상
- 진짜 이중 데미지인지 표시 문제인지부터 갈라야 했음

### 고민

■ actionBySlot 을 지워도 되는가 — 소유권 확인
- 생성자 주입 사전이라 외부 소유자가 있으면 Clear 가 부작용이 됨
- BattleRuntime.cs:44 가 new Dictionary 를 즉석 생성해 넘김 → BoutGraph 단독 소유, 지워도 안전

■ 로그 2번의 원인 분리
- HP 는 정확히 1번만 깎임 → 엔진은 무죄
- HpUI.OnDamage 첫 줄의 진단용 Debug.Log 가 characterId 필터 "앞"에 있었음
- 씬에 HpUI 가 2개(id 0/1) → DamageLog 1건에 구독자 2명이 각자 찍음 = 2줄

### 해결법

- Clear() 에 actionBySlot.Clear() 추가 (플레이로 슬롯 비워짐 확인)
- HpUI 의 진단 Debug.Log 삭제 — 역할(HP 반영 확인)을 다한 임시 코드였음

### 배운 점

- 공유될 수 있는 컬렉션을 비울 땐 먼저 소유권(누가 만들어 넘겼나)을 확인한다
- "N번씩 찍히는 로그"는 이벤트가 N번 발생한 것과 구독자가 N명인 것을 먼저 구분한다.
  모델 값(HP)이 1번만 변했다면 발생은 1번이다
- 진단용 임시 로그는 목적을 다하면 바로 지운다. 필터 앞에 둔 로그는 구독자 수만큼 증폭된다
