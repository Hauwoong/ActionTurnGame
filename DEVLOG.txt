### 오늘 한 것

- 주사위(DiceData) 기반 카드 효과 처리 구조 설계
- 카드 → 주사위 → 전투 처리 흐름 설계

- BattleContext 기반 전투 정보 전달 구조 설계
- CardUI ↔ BattleManager ↔ CardData 연동 구조 개선
- 카드 효과 처리 로직 설계 및 테스트

### 문제
- CardData 추상 클래스와 virtual / abstract 혼용으로 컴파일 오류 발생
- BattleContext 전달 구조 설계 미흡으로 UseCard 호출 오류 발생
- CardData.Use / Resolve 구조 혼란으로 인한 타입 불일치 오류

### 해결
- CardData 구조를 추상 기반 공통 처리 + 데이터 중심 구조로 재설계
- 카드 사용 시 BattleContext를 통해 전투 정보 전달하도록 구조 수정
- 카드 타입 분류(enum) 제거 → 주사위 데이터 중심 구조로 통합
- 기본 카드와 특수 카드 상속 구조 방향 정립
- 카드 역할을 주사위 조합으로 표현하는 방식 확정

### 배운 점
- 카드 시스템의 핵심은 “카드 타입”이 아니라 “행동 데이터”이다
- ScriptableObject + 데이터 중심 구조는 확장성이 매우 높다
- abstract / virtual은 역할이 명확할 때만 사용하는 것이 좋다
- BattleContext 같은 컨텍스트 객체는 시스템 결합도를 낮춰준다
- 중복 구조를 의심하고 제거하는 설계가 장기 유지보수에 중요하다

### 문제 — 중요한 실수 기록

■ "참조 0건"을 "지워도 되는 코드"로 착각
- Bout.cs 는 어디서도 참조되지 않았지만 "개념이 살아있다"는 이유로 존치 결정

- 컴파일 실패 상태의 Unity 는 Add Component 를 거부 → "컴포넌트가 안 붙는다"는 증상으로 나타남
- 참조 수와 컴파일 가능 여부는 별개다

■ IRng.Range 의 경계 규약이 문서화되지 않음
- DeterministicRng.Range 는 random.Next(min, max + 1) → max 포함
- Unity 의 Random.Range(int, int) 는 max 제외 → 그 관습을 아는 사람일수록 착각
- CardZone.Shuffle 이 rng.Range(0, i + 1) 로 작성됨 → ArgumentOutOfRangeException
- 덱이 비었을 땐 루프가 안 돌아 드러나지 않다가, 카드를 넣는 순간 터짐
- 주사위/속도 호출부는 포함 기준이 맞아 정상 동작 → 셔플만 틀린 채로 잠복해 있었음

■ using UnityEngine 이 없어도 Unity 에 종속될 수 있음
- BattleSnapShot 은 using UnityEngine 이 없는데 IEnumerable<Character> 를 받고 있었음
- Character 는 MonoBehaviour → 타입 참조만으로 종속
- 계층 순수성은 using 목록이 아니라 시그니처에 등장하는 타입으로 판단해야 함

■ Editor.log 는 누적된다
- 이미 삭제된 파일의 과거 에러가 그대로 남아 있음
- error CS 를 grep 할 때 해당 파일/멤버가 현재도 존재하는지 교차 확인 필요

■ 호출자 없는 코드가 대량으로 방치돼 있었음
- CreateBattle / StartTurn / ExecuteCombat / EndBattle 모두 호출자 0
- EndTurn 만 TurnUI 버튼에 연결돼 있었고, 그마저 ExecuteCombat 을 부르지 않아
  등록한 액션이 해석 없이 BoutGraph.Clear() 로 버려지고 있었음
- 컴파일이 되는 것과 실행 경로가 이어진 것은 별개다

■ 진영 개념 부재
- BattleSnapShot 이 양 진영을 평평한 리스트 하나로 합쳐 받아 팀 정보가 소실
- IsBattleOver() 가 전체 생존자 수만 세어 사실상 "최후의 1인" 규칙이 됨
- 3v3 에서 한 팀이 전멸해도 전투가 끝나지 않는 상태였음

### 해결
- Bout.cs / BoutCandidate.cs 삭제, LorRuleSet 계열 삭제
- enum Team 도입, IsBattleOver() → TryGetBattleResult(out Team? winner) 로 교체
- BattleStarter 신설, EndTurn 이 턴 진행 순서(전투 해석 → 종료 판정 → 다음 턴)를 소유
- BattleManager 가 Character → CharacterData 추출을 담당, BattleSnapShot 은 순수 데이터만 수신
- 추출은 즉시 평가. 지연 평가(LINQ Select)로 넘기면 멤버 접근이 다시 엔진 안에서 일어남
- CardZone.Shuffle 은 rng.Range(0, i) 로 수정. IRng.Range 는 이름/주석으로 규약 명시 검토 중

### 배운 점
- 데드 코드는 "안 쓰인다"와 "컴파일된다"를 따로 확인해야 한다
- 난수 API 는 경계 규약을 이름이나 주석에 드러내야 한다. Range 라는 이름은 Unity 관습 때문에 오해를 부른다
- 계층 순수성은 using 이 아니라 시그니처로 판단한다
- 인스펙터 필드는 타입에 따라 넣을 것이 다르다 — Character 는 씬 오브젝트, CharacterData 는 에셋
- 잘못된 세팅은 NullReferenceException 이 아니라 위치(진영/인덱스/이름)를 담은 메시지로 드러나야 원인 추적이 빠르다
- 버그가 "지금까지 안 터진 것"이 "정상이었다"는 뜻은 아니다. 조건이 안 맞아 잠복했을 뿐일 수 있다

## 2026-07-22 — 데미지가 HP UI 에 반영되지 않던 문제 (이벤트 실행 순서)

합은 잡히는데 HP 텍스트가 계속 50 → 원인을 파이프라인 끝에서 끝까지 추적한 기록.

### 문제점

■ 주사위를 캐릭터 큐에 싣는 단계가 파이프라인에서 통째로 빠져 있었음
- 카드 등록(ActionRegisteredEvent → BoutGraph)은 되는데, 그 카드의 주사위를 싣는 CharacterRuntime.UseAction 호출자가 0 건
- 그래서 ResolveCombat 이 PeekDice == null 로 즉시 탈출 → 데미지 0, 카드도 슬롯에 잔류
- 클래시 자체가 아니라 "합은 걸리는데 데미지가 안 나오는" 증상으로 나타남

■ 데미지는 실제로 들어가는데 HP 텍스트만 50 에서 안 변함 (이번 기록의 핵심)
- 임시 로그로 확인: [Damage] target=0 amount=1 이 찍히고, 스택도 DamageEvent → AddLog → HpUI.OnDamage 까지 정상 도달
- 즉 모델 HP 는 깎이고 있는데 화면만 stale

■ 3턴이 지나면 데미지가 더 이상 안 들어감
- 에너지(빛)가 소비만 되고 회복이 없음. maxEnergy 3, cost 1 → 3턴이면 0
- 등록은 에너지를 검사하지 않고 UseAction(해석 시점)만 검사 → 합은 걸리는데 조용히 데미지 0

■ (부수 발견) BoutGraph.Clear() 가 actionBySlot 을 안 지움
- edges/targetMap/interceptCandidates 만 clear → 턴이 넘어가도 슬롯에 카드 이름이 남음

### 고민

■ HP 텍스트가 안 변하는 진짜 원인
- AddLog 은 동기다. 그 한 줄이 Dispatch → HpUI.OnDamage → Refresh 까지 그 자리에서 다 실행하고 리턴한다
- Refresh 는 cr.CurrentHp 를 그 순간 다시 읽는다 → "언제 읽느냐"가 전부
- 고치기 전 DamageEvent 는 AddLog(로그) → TakeDamage(HP 감소) 순이었다
  → Refresh 가 아직 안 깎인 HP 를 읽어 그림. 모델은 그다음에야 깎임. UI 는 영원히 한 박자 전 값

■ "로그 먼저" vs "상태 먼저" — 어느 쪽이 규칙인가
- CLAUDE.md 규칙은 "AddLog → CharacterRuntime 호출" (로그 먼저)로 적혀 있었음
- 실제 코드를 세어보니 8 개 중 5 개는 이미 "상태 먼저"(EnergyUse/ChangeMaxHp/GainEmotionStack/Draw/Death)

## 2026-07-22 — 일방 공격이 통째로 증발하던 버그 (CombatExecutor)

배경: 상대가 카드를 내지 않은 슬롯을 때리면 아무 일도 일어나지 않았다.
ResolveUnopposedDice 와 BoutStartEvent(action, null, ...) 경로는 진작 구현돼 있었는데
도달하는 코드가 없던 상태.

### 문제점

■ 타겟을 action 이 아니라 graph.edges 에서만 찾고 있었음
- RunQueue 의 `if (!graph.edges.TryGetValue(slot, out var targetSlot)) continue;`
- edge 는 BoutGraph.Connect 가 양방향으로만 만든다 = 양쪽이 서로를 겨냥해야 생긴다
- 즉 "합이 성립한 공격"만 처리되고, 합이 아닌 공격(일방)은 전부 continue 로 증발
- 덤으로 이 continue 는 visited.Add 도 하지 않는 유일한 탈출 경로였음

### 고민

■ "edge 없으면 폴백 targetSlot 만 구해서 기존 흐름에 태우면 되지 않나?" → 안 됨
- 내 타겟이 제3자를 노리는 액션을 갖고 있으면(edge 없음, ActionBySlot 에는 있음)
  기존 클래시 조건이 그걸 opponent 로 잡아 성립하지도 않은 합을 만들고,
  상대를 visited 처리해 상대의 진짜 합까지 날린다
- edge 없음 = 무조건 일방 경로. 클래시 조건에 hasEdge 를 명시해야 함

■ TryGetValue 실패 시 out 값의 함정
- SpeedSlot 은 struct → 실패 시 null 이 아니라 default = (characterId 0, slotIndex 0)
- 멀쩡해 보이는 값이라 그대로 흘리면 무조건 0번 캐릭터를 때린다
- 폴백은 반드시 action.TargetSlot 에서 가져와야 함 (이미 손에 든 action 에 붙어 있음 —
  ActionBySlot 재조회 불필요)

### 해결법

■ RunQueue 재구조화 (체크리스트 방식으로 구현)
1. bool hasEdge = graph.edges.TryGetValue(slot, out var targetSlot)
2. !hasEdge 면 targetSlot = action.TargetSlot 으로 대체
3. IsTargetAlive 검사는 공통 경로에서 통과
4. 클래시 조건에 hasEdge 추가 → edge 없으면 자동으로 else(일방)행
5. 모든 탈출 경로가 visited.Add(slot) 을 찍는 것 확인

■ 플레이 검증
- 빈 슬롯 공격 → 데미지 반영 확인
- 정상 합 회귀 없음, 다음 턴 정상 진행

### 배운 점

- struct 를 out 으로 받는 TryGetValue 는 실패해도 "그럴듯한 값"(default)을 돌려준다.
  참조 타입의 null 처럼 터져 주지 않으므로, 실패 분기를 안 만들면 조용히 엉뚱한 대상을 가리킨다
- "경로가 구현돼 있다"와 "경로에 도달한다"는 별개다. 일방 공격 처리 코드는 완성돼 있었지만
  호출부의 필터가 그 앞에서 전부 걸러내고 있었다
- 루프의 탈출 경로마다 불변식(여기선 visited 마킹)이 지켜지는지 경로별로 세어봐야 한다.
  한 경로만 빠뜨려도 "가끔 두 번 처리되는" 류의 버그가 된다

- Bleed 에 duration 1 을 주면 스택이 절반으로 줄어드는 로직이 두 번째 기회를 못 받는다
- Stack/2 와 if (Stack <= 0) IsExpired 를 이미 써 뒀다는 건 스택 소모로 만료시킬 의도였다는 뜻
- 즉 duration 1 은 그 코드를 죽은 코드로 만든다 → 만료 방식을 효과별로 하나만 쓰도록 갈랐다

■ duration 을 누가 정하나 — 호출자냐 효과 타입이냐
- 호출자가 넘기면 AddStatus → StatusAddEvent → 카드 데이터까지 인자가 번진다
- 지속시간은 효과의 성질이므로 서브클래스가 자기 기본값을 하드코딩하는 쪽 채택
- 반대로 "다음 턴에 부여"(발효 시점)는 카드의 성질이라 효과 클래스에 넣으면 안 된다 —
  같은 힘을 즉시 주는 카드와 다음 턴에 주는 카드가 공존할 수 있기 때문. 축이 다르다

■ base 에 라이프사이클 로직을 두면 오버라이드가 base 를 안 부를 때 조용히 깨진다
- Burn 이 이미 그 사고를 낸 전례 → 감소·만료를 오버라이드 불가능한 래퍼로 올림

■ 로그에 요청량을 담나 결과를 담나
- AddStatus(Strength, 3) 인데 이미 힘 2가 있으면 결과는 5. 요청량을 담으면 UI 가 틀린 값을 그린다
- EnergyRecoverLog 를 "실제 회복량"으로 정한 선례가 있어 동일하게 결과값 채택

### 해결법

■ 훅 순회 (8개 Trigger*)
- _statusEffects.ToArray() 스냅샷 위에서 순회 + 루프 첫 줄 if (effect.IsExpired) continue
- FlushExpired 호출 위치를 "상태이상 루프 직후 → 패시브 루프" 로 8곳 통일
- TriggerTurnEnd 에만 빠져 있던 EnsureSorted() 추가
- _passives 는 생성자에서만 채워지고 제거가 없어 스냅샷 불필요

■ FlushExpired
- 역순 루프에서 참조를 먼저 잡고 RemoveAt(i) → _effectMap 은 ReferenceEquals 로
  동일 인스턴스일 때만 제거 (좀비를 지우면서 새 인스턴스의 맵 항목을 날리지 않도록)

■ duration 배선
- StatusEffectRuntime 생성자에 int duration 추가, public const int Permanent = -1 센티널
- TickTurnEnd(비-virtual 래퍼)가 OnTurnEnd() → Duration 감소 → 만료 판정 순으로 독점
- OnTurnEnd 를 public → protected 로 내려 CharacterRuntime 이 래퍼를 우회할 수 없게 함
- 값: Bleed/Burn = Permanent(스택 소모형), Strength/Paralysis = 1(턴 카운트형)
- Refresh() + readonly _baseDuration — 재적용 시 지속시간 갱신 (AddStatus 의 AddStack 옆)

■ StatusAddEvent / StatusAddLog 신설
- Apply 는 GetCharacterRuntime → AddStatus → AddLog 순 (핵심 규칙: 상태 먼저, 로그 나중)
- AddStatus 를 int 반환으로 바꿔 결과 스택을 로그에 싣는다

### 배운 점

- 이벤트 큐가 DFS 재귀라 훅 순회 중 재진입이 일어난다. EnqueueEvent 를 부르는 훅은
  그 자리에서 같은 객체의 다른 훅으로 되돌아올 수 있다 — 앞으로도 계속 물릴 함정이다
- 순회 중 컬렉션을 건드리는 문제는 "복사해서 돌기"와 "순회 중 변경을 금지하기" 두 갈래다.
  전자는 증상을, 후자는 원인을 없앤다
- 라이프사이클 관리는 오버라이드 불가능한 래퍼로 올리고, 훅은 protected 로 내린다.
  그러면 우회가 컴파일 에러가 되어 컴파일러가 규칙을 강제한다 (Burn 사고의 재발 방지)
- 센티널 값을 쓸 땐 판정을 가드 블록 "안"에 넣는다.
  if (Duration > 0) Duration--; 와 if (Duration <= 0) IsExpired = true; 를 나란히 두면
  Permanent(-1)가 두 번째에 걸려 정반대로 작동한다 — 실제로 겪음
- TryGetValue 의 out var 는 else 분기에서 null 이다. 분기 밖에서 그 변수를 쓰려면
  else 에서 재대입해 "최종적으로 사용된 값"을 가리키게 만든다
- 참조 0건인 채로 작성한 코드는 "아직 검증되지 않은 코드"다. 컴파일이 통과해도
  한 번도 실행된 적이 없다는 사실은 변하지 않는다
- 도메인을 알아야만 판단할 수 있는 코드가 있다. Refresh() 는 duration 이 1이나 Permanent 뿐인
  현재 규칙에서는 영구 no-op 인데(0이 되는 순간 IsExpired 가 함께 켜지므로 Refresh 시점의
  Duration 은 항상 1 이상), 참조도 있고 컴파일도 되고 테스트로도 안 잡힌다.
  원작에 "N턴 지속" 버프가 없다는 사실을 아는 사람만 알 수 있다

## 2026-07-27 — 상태이상 Delay(발효 지연): 설계를 바꾸니 계획의 절반이 사라졌다

■ 계획대로 IsActive 가드를 순회 루프에 넣으면 delay 가 영영 안 깎인다
- 가장 손이 적은 방법은 CharacterRuntime 의 8개 루프에서 !IsActive 를 걸러내는 것
- 그런데 delay 를 줄이는 곳이 TickTurnEnd 다. 비활성 효과를 루프에서 걸러버리면
  TickTurnEnd 자체가 호출되지 않아 대기 중인 힘이 영원히 대기한다
- 즉 TickTurnEnd 는 비활성일 때도 돌아야 하고 나머지 7개는 돌면 안 된다는 비대칭이 있었다

■ 굴림 보정이 일방 공격에서 통째로 빠진다 (작업 중 발견, 3-1.7 로 분리)
- TriggerBeforeClash 호출자가 ResolveDiceClash 안의 두 줄뿐
- 힘/마비만이 아니라 AttackBoostPassive 까지 일방에서 죽는다

### 고민

■ 즉시분과 대기분이 겹칠 때 이번 턴 보정은 얼마인가
- Min(기존, 신규) 로 delay 를 병합하면 구현은 가장 작지만 "다음 턴에 쓰려고 건 힘"이 앞당겨진다
- 원작은 즉시분과 대기분을 따로 센다(사용자 확인) → PendingStack 채택
- 이 답이 나오는 순간 설계가 바뀌었다. 대기분이 별도 숫자라면 훅들은 그냥 Stack 만 읽으면 되고,
  "대기 중이라 훅을 막아야 하는 상태"가 아예 존재하지 않는다.
  Delay 카운터도 IsActive 도 래퍼 7개도 전부 증발했다

■ delayed 를 생성자로 뚫을 것인가 AddStack 으로 받을 것인가
- 생성자로 뚫으면 서브클래스 4개 + StatusFactory 까지 번지고, 그러고도 분배 규칙이 두 군데 생긴다
  (신규 생성은 생성자가, 기존 효과는 AddStack 이 각각 "delayed 면 어디에 넣나"를 알아야 함)
- AddStack(amount, delayed) 하나로 몰고 AddStatus 를 "만들고 → 등록하고 → 채운다"로 합치는 쪽 채택

### 해결법

■ Stack / PendingStack 두 칸
- AddStack(int amount, bool delayed) 이 분배를 독점
- 훅은 Stack 만 읽으므로 대기분은 자연히 제외된다

■ TickTurnEnd 순서 — 이게 설계의 전부다
1. OnTurnEnd()
2. duration 만료면 활성분 버리기 (Stack = 0)
3. 대기분 승격 + Duration = _baseDuration 재장전
4. 그러고 나서 만료 판정
- 2를 빼면 즉시 2 + 대기 3 이 5가 된다(규칙은 3)
- 3의 재장전을 빼면 duration 이 0에 머물러 승격분이 만료 판정을 못 받는다
- 4를 2 자리로 올리면 승격된 스택이 IsExpired 를 켠 채로 FlushExpired 에 쓸려나간다
- 1이 3보다 앞이어야 "다음 턴에 화상"이 이번 턴에 터지지 않는다

■ Bleed/Burn 은 가드가 두 개 필요했다
- 진입 가드 if (Stack <= 0) return; — 순수 대기분일 때 0 데미지 이벤트와 오발 만료를 막는다
- 만료 조건 && PendingStack <= 0 — 즉시 1 + 대기 5 처럼 "나가면서 0이 되는" 경우를 막는다
- 하나만 넣으면 다른 쪽이 뚫린다. 서로 다른 순간을 보는 가드다

### 배운 점

- 규칙을 먼저 확정하면 구현 형태가 따라 정해진다. "대기분을 따로 센다"는 답 하나로
  Delay 필드 + IsActive + 래퍼 7개가 통째로 사라졌다. 코드를 먼저 짰으면 전부 만들었을 것이다
- 계획서에 적힌 설계도 규칙이 확정되면 다시 봐야 한다. CLAUDE.md 에 적혀 있다는 게 검증된다는 뜻은 아니다
- 복잡도는 없앨 수 없을 때가 있지만 한 곳으로 모을 수는 있다. 여기서는 TickTurnEnd 로 모였고,
  그래서 순서 네 줄만 맞추면 되는 문제가 됐다
- 리팩터링 중에 등록 코드가 조용히 사라질 수 있다. 두 분기를 합치면서 _statusEffects.Add 와
  _effectMap 대입이 같이 없어졌는데, 컴파일은 통과하고 증상은 "상태이상이 아예 안 걸린다"였다
- 조건을 뒤집은 버그는 플레이 테스트로 안 잡힐 수 있다. !IsExpired 를 잘못 써서 살아있는 효과에
  매번 새 인스턴스를 만들었는데, 리스트에 옛 인스턴스가 남아 훅이 두 번 돌기 때문에
  "힘 2회 → 스택 6" 테스트가 그대로 통과했다. 값이 우연히 맞는 버그가 제일 오래 산다
- IDE 자동 import 가 Engine 순수성을 깬다. using Unity.VisualScripting 이 자동완성으로 들어왔었다.
  경계(asmdef)가 없으면 실수가 조용히 통과한다 — 4단계의 값어치가 "의존을 끊는다"에서
  "실수로 의존이 생기는 걸 기계가 막는다"로 늘었다

## 2026-07-27 — 상태이상 UI, 그리고 UI 를 붙이자마자 드러난 순서 버그

배경: 힘·마비를 브레이크포인트로만 확인해야 했던 상황을 끝내려고 StatusUI 를 만들었다.
만들면서 출혈·화상이 "핵심 규칙"을 어기고 있다는 게 드러났다.

### 문제점

■ 상태이상 변경 중 자기 로그를 가진 건 부여 하나뿐이다
- StatusAddLog 만 구독하면 부여 순간만 맞고 그 뒤로는 계속 틀린 값을 그린다
- 로그가 없는 변경: 출혈·화상 스택 절반 감소 / 만료(FlushExpired) / 대기분 승격 / duration 감소
- 출혈 5 를 걸고 굴림을 세 번 해도 UI 는 5 를 유지한다

■ 출혈·화상이 "로그 먼저, 상태 나중" 이었다
- OnDiceRoll 이 EnqueueEvent 를 부른 뒤에 Stack = Stack / 2 를 했다
- EnqueueEvent 는 동기라 그 자리에서 StatusDamageLog 까지 나가고, UI 가 그걸 받아 모델을 읽는다
- 그 시점의 Stack 은 아직 안 깎인 값 → UI 가 한 박자 밀린다
- 2026-07-22 에 DamageEvent 에서 겪었던 바로 그 버그다. 규칙에 적어뒀는데도 새로 쓴 코드가 어겼다

  그 뒤 FlushExpired 로 제거되지만 로그가 안 나가서 화면엔 Bleed 0 이 남는다

### 고민

■ 로그 없는 변경들을 위해 로그를 새로 만들 것인가

- 대신 "그 변경들이 이미 다른 로그와 같은 순간에 일어난다"는 점을 봤다.
  스택 감소는 StatusDamageLog 와 같은 자리, 만료·승격·duration 은 전부 TriggerTurnEnd 안이고
  TurnEndLog 가 그 뒤에 나간다 → 기존 로그 4개 구독으로 해결

■ 노출을 프로퍼티로 할 것인가 조회 메서드로 할 것인가
- SpeedSlots 선례를 따라 IReadOnlyList 프로퍼티. 인자 없이 컬렉션을 돌려주는 건 프로퍼티가 관례고,
  Get- 메서드는 계산이 일어난다는 인상을 준다
- IReadOnlyList 는 리스트 구조만 막고 원소는 못 막는다는 한계는 남는다.
  완전히 막으려면 읽기 전용 view 타입이 필요한데 SpeedSlots 까지 같이 바꿔야 의미가 있어 미뤘다

■ 빈 목록을 빈 문자열로 둘 것인가
- 빈 문자열이면 "상태이상이 없다"와 "UI 가 안 돌고 있다"가 구분이 안 된다 → "-" 로 채웠다

### 해결법

■ StatusUI 는 HpUI 뼈대 그대로 (OnEnable/OnDisable/Bind/Unbind/Refresh + characterId 필터)
- 구독 4개: StatusAddLog / StatusDamageLog / TurnEndLog / TurnStartLog
- Refresh 는 IsExpired 를 건너뛰고 parts 리스트에 모아 string.Join(" | ")
- PendingStack > 0 이면 "(+n)" 을 덧붙여 3-2 가 눈에 보이게

■ 출혈·화상 순서 교정 — ctx 생성 → Stack 감소 → 만료 판정 → EnqueueEvent
- ctx 가 깎기 전 값을 이미 붙잡아두므로 데미지 수치는 그대로다

### 배운 점

- 규칙을 문서에 적어두는 것만으로는 안 지켜진다. "상태 먼저, 로그 나중"은 CLAUDE.md 핵심 규칙에
  있는데도 이번에 새로 쓴 출혈·화상이 둘 다 어겼다. 강제하는 장치가 없으면 반복된다
- UI 를 붙이면 엔진 버그가 드러난다. 브레이크포인트로 볼 때는 순서가 안 보였다 —
  멈춰서 보면 최종 값만 보이니까. 실시간으로 그리기 시작하니 중간 상태가 노출됐다
- 관측 수단을 만드는 일은 기능 개발이 아니라 검증 인프라다. 우선순위를 뒤로 미루면
  그 뒤의 모든 작업이 조금씩 더 비싸진다. 힘·마비를 브레이크포인트로 본 게 이틀이었다
- 로그를 새로 만들기 전에 "이 변경이 이미 다른 로그와 같은 순간에 일어나는가"를 먼저 볼 것.
  같은 순간이면 구독 하나로 끝난다
- UI 가 모델을 다시 읽는 구조면 로그의 내용은 안 쓰인다. 그래서 StatusAddLog 에 delayed 를
  추가하려던 계획이 불필요해졌다 — 로그는 "뭔가 바뀌었다" 신호로만 기능한다

## 2026-07-29 ~ 07-30 — 굴림 보정이 일방 공격에서 통째로 빠지던 문제 (3-1.7 / 3-1.8 / 3-1.9)

배경: 3-1.5(출혈)와 같은 계열의 마지막 비대칭. 출혈은 "굴림 훅이 일방에 없다"였고
이번은 "굴림 보정 훅이 일방에 없다"였다. 범위는 이쪽이 더 넓어서 상태이상만이 아니라 패시브까지 걸려 있었다.

### 문제점

■ OnBeforeClash 를 쓰는 것 전부가 일방 공격에서 죽는다
- TriggerBeforeClash 호출자가 ResolveDiceClash 안의 두 줄(CombatExecutor.cs:122-123)뿐
- ResolveUnopposedDice 는 entry.Dice.CurrentRoll 을 날것으로 DamageContext 에 넣는다
- 피해자: 힘(StatusEffects.cs:42,44), 마비(:57,59), AttackBoostPassive(:16,18)
- 3-1.5 로 굴림 훅은 메꿔졌으므로 일방에서 빠지는 훅은 OnBeforeClash 하나뿐이었다

■ 근본 원인은 ClashContext 가 두 가지를 한 그릇에 담고 있던 것
- "주사위 하나의 최종 굴림값"(ModifiedRollA/B)과 "두 주사위의 비교"가 같은 타입에 있다
- 힘은 앞엣것인데 뒤엣것에 묶여 있어서, 비교 상대가 없으면 같이 사라진다
- 훅 시그니처가 (ClashContext ctx, bool isOwnerA) 인 것 자체가 그 결합의 증상이다.
  자기 주사위만 건드리는 효과가 A/B 중 누구인지를 알아야 했다

■ 방어·회피 주사위를 일방에서 굴리고 있었다 (작업 중 발견)
- 그 주사위는 Consume 으로 보관됐다가 BoutEndEvent → DiceRecoverEvent 로 Ready 로 돌아온다
- 즉 나중에 다시 굴려질 것을 전제로 하므로 지금 굴린 값은 버려진다
- 그런데 3-1.5 가 Roll 직후에 TriggerDiceRoll 을 넣어둬서, 버릴 굴림에 출혈이 터지고 있었다

### 고민

■ A안(굴림 전용 컨텍스트 신설) vs B안(일방에서도 ClashContext 재사용)
- B안은 변경이 작지만 상대 주사위 자리가 null 이 되고, "클래시가 아닌데 ClashContext" 라는
  이름/실체 불일치가 남는다. 3-1.5 에서 배운 것과 정면으로 부딪힌다
- A안은 두 경로가 같은 훅을 공유하게 되므로 같은 종류의 누락이 재발하지 않는다 → A안

■ 힘·마비가 방어·회피 주사위에도 붙는가
- AttackBoostPassive 는 DiceType.Attack 을 검사하는데 힘·마비는 안 하고 있었다.
  둘 중 하나는 틀린 상태였다는 뜻이다
- 사용자 확인: 힘 = 공격 주사위만, 마비 = 전 타입
- 효과마다 범위가 다르므로 타입 검사는 호출부 일괄이 아니라 각 훅 구현 안에 둔다

■ 굴림값 하한 1 을 어디에 걸 것인가
- 마비 안에 거는 안: 지금은 동작한다. 감소 효과가 마비뿐이고 priority 상 힘 다음이라
  그 뒤로는 더할 일만 남기 때문이다. 하지만 순서 의존이고, 감소 효과가 하나 더 생기면
  각자가 클램프를 다시 구현해야 한다
- "하한 1"은 마비의 규칙이 아니라 주사위의 규칙이다 → 불변식의 소유자는 래퍼여야 한다
- 두 방식은 결과도 다르다. 굴림 3 / 마비 5 / 힘 2 일 때
  마비 안 클램프 = (3-5→1)+2 = 3, 래퍼 클램프 = 3-5+2 = 0 → 1
- 원작이 "보정 합산 후 하한" 이므로 래퍼(TriggerModifyRoll 반환 직전)로 확정.
  TickTurnEnd 가 duration 감소를 독점하는 것과 같은 구도다

■ 보정된 값을 DiceRuntime.CurrentRoll 에 되쓸 것인가
- 안 쓴다. CurrentRoll 은 "주사위가 실제로 뭘 굴렸나", ModifiedRoll 은 "이번 해석에서 쓸 값"으로
  다른 개념이다. 합치면 원본을 되찾을 방법이 없어져서 "최대값 굴림 시 발동" 류를 못 만든다
- 구조적으로도 CurrentRoll 은 { get; private set; } 이고 쓰는 곳이 Roll() 하나뿐이다.
  되쓰려면 setter 를 열어야 하고 그러면 굴림값의 출처 추적이 불가능해진다
- 로그(DiceClashLog)가 보정 전 값을 찍어 헷갈리는 건 별개 문제. 고칠 거면 로그에 넘기는 값을
  바꾸는 것이지 주사위를 바꾸는 게 아니다. 검증 중에 하면 원인 구분이 안 되므로 미뤘다

■ TriggerModifyRoll 을 타입 검사 밖에 둘 것인가 안에 둘 것인가
- 처음엔 "밖"으로 정했다. 합 경로가 타입 무관하게 도니 대칭이 맞고,
  나중에 마비를 스택 소모형으로 바꾸면 "굴렸는데 훅이 안 돌았다"가 버그가 되기 때문
- 그런데 방어·회피는 애초에 굴리면 안 된다는 게 드러나면서 전제가 무너졌다
- 결론이 뒤집혀 "안"으로. 대신 원칙을 다시 세웠다:
  Roll() 이 있는 자리에 굴림 훅이 따라붙는다. 굴리지 않으면 훅도 없다

### 해결법

■ DiceRollContext 신설 (Owner / Dice / ModifiedRoll)
- Owner·Dice 는 get 전용. 훅 순회 도중 대상이 바뀌면 뒤에 도는 효과가 다른 주사위를 본다
- ModifiedRoll 은 생성자에서 dice.CurrentRoll 로 초기화. 호출부가 넘길 값이 그것뿐이라
  인자로 두면 틀릴 여지만 생긴다
- IsCancelled 는 넣지 않았다. 굴림에 취소 개념이 없고, 넣으면 IClashContext 를 구현하고 싶어진다

■ OnModifyRoll 훅을 StatusEffectRuntime / PassiveEffect 양쪽에 추가
■ CharacterRuntime.TriggerModifyRoll(DiceRuntime dice) → int
- 골격은 기존 Trigger* 와 동일 (EnsureSorted → ToArray 스냅샷 + IsExpired 건너뛰기 → FlushExpired → 패시브 루프)
- TriggerDiceRoll 을 베끼면 안 된다. 그건 패시브 루프가 없는 유일한 훅이라 AttackBoostPassive 가 빠진다
- 반환 직전 Math.Max(1, ctx.ModifiedRoll). Mathf 가 아니라 System.Math (Engine 은 UnityEngine 무의존)

■ 세 구현체 이사 — 힘(타입 가드 있음) / 마비(타입 무관) / AttackBoostPassive
- isOwnerA 분기가 통째로 사라져 셋 다 한 줄이 됐다. 훅이 자기 주사위 하나만 보기 때문

■ 배선
- ResolveDiceClash: Roll 두 번 → 주사위별로 TriggerModifyRoll → 그 값으로 ClashContext 생성.
  TriggerBeforeClash 두 줄 삭제
- ClashContext 생성자가 modifiedRollA/B 를 인자로 받게 변경 (기존엔 자기가 CurrentRoll 로 초기화)
- ResolveUnopposedDice: 타입 검사를 Roll 위로 올려, 공격이 아니면 굴리지 않고 DiceConsumedEvent 만 내고 빠짐.
  공격이면 Roll → TriggerDiceRoll → TriggerModifyRoll → DamageContext

■ ClashContext 가 DiceA/DiceB 를 잃었다
- 타입 검사가 훅 안으로 들어가면서 참조 0건이 됐다. 이제 "두 캐릭터 + 두 숫자"만 남는다

■ 삭제 3건
- OnBeforeClash (StatusEffectRuntime / PassiveEffect) + TriggerBeforeClash — 사용자 0
  → 3-1.9 의 파라미터명 IsOwnerA 대소문자 문제도 이 줄과 함께 소멸
- ClashContext 의 : IClashContext 와 Defender (3-1.8).
  IClashContext 자체는 DamageContext/StaggerContext/ClashContextEvent 에서 계속 쓰이므로 남는다
- StatusEffectRuntime.Refresh() — 3-2 에서 호출이 사라진 뒤 참조 0, 게다가 no-op (3-1.9)

■ 검증 — 대조군을 먼저 만들었다 (3-1.5 선례)
- 고치기 전: 힘을 걸고 일방 공격 → 데미지가 굴림값 그대로
- 고친 뒤: 같은 세팅에서 힘만큼 상승
- 합 회귀(양쪽 굴림값이 서로 다르게 나오는지), 출혈 5→2→1 회귀 없음 확인
- 방어·회피 주사위 관련은 카드가 Strike(Attack 1개)뿐이라 여전히 검증 불가

### 겪은 실수

■ ClashContext 생성자 복붙 — ModifiedRollB = modifiedRollA
- 이대로면 B의 굴림값이 항상 A와 같아져 모든 합이 무승부가 되고, 힘·마비도 A 것만 양쪽에 적용된다
- 새로 만진 배선(5번)이 원인처럼 보이는 증상인데 실제로는 한 글자였다

■ 타입 검사를 위로 올리면서 주사위를 소비하지 않고 return
- ResolveCombat 의 while (true) 는 PeekDice 가 null 이 될 때까지 돌고,
  주사위는 DiceConsumed/DiceDestroyed 이벤트로만 줄어든다 → 무한 루프
- 공교롭게도 며칠 전 "IsCancelled 를 굴림 컨텍스트에 넣으면 안 되는 이유"로 예측했던 실패가
  다른 경로로 그대로 재현됐다. 이 루프에서 "아무것도 안 하고 빠지기"는 존재하지 않는다
- RunQueue 가 모든 탈출 경로에 visited.Add(slot) 을 찍어야 했던 것과 같은 구조다

### 배운 점

- 훅 시그니처에 "나는 A인가 B인가"가 들어 있으면 그건 컨텍스트가 너무 크다는 신호다.
  효과 입장에서 필요한 건 자기 주사위 하나뿐인데 두 주사위짜리 그릇을 받고 있었고,
  그래서 상대가 없는 상황에서 통째로 못 쓰이게 됐다. 그릇을 쪼개니 분기가 저절로 사라졌다
- 같은 계열의 버그는 한 번 더 온다. 3-1.5 를 고칠 때 "일방 경로에서 빠지는 훅이 또 있나"를
  전수조사해뒀기 때문에 이번엔 찾는 데 시간이 안 들었다. 고친 직후가 주변을 훑기 가장 싼 시점이다
- 불변식은 그걸 어길 수 있는 모든 곳이 아니라 통과할 수밖에 없는 한 곳에 둔다.
  하한 1 을 마비에 두면 감소 효과가 늘 때마다 재구현해야 하고, 래퍼에 두면 한 번으로 끝난다.
  TickTurnEnd 와 같은 판단이다
- 전제가 바뀌면 결론을 뒤집어야 한다. "훅을 타입 검사 밖에" 는 방어 주사위도 굴린다는 전제 위의
  판단이었고, 그 전제가 틀렸다는 게 드러난 순간 반대가 됐다. 대신 남길 것은 결론이 아니라 원칙이다
  ("Roll 이 있는 자리에 굴림 훅이 따라붙는다")

### 남은 것 / 새로 발견

■ DiceRecoverEvent 가 실제로는 효과가 없어 보인다 (미확인, 별도 작업)
- Advance(Consume) 가 _cursor++ 를 하는데 Recover() 는 상태만 되돌리고 _cursor 는 안 건드린다
- Peek() 은 _cursor 부터 앞으로만 훑고, Inject 는 새 주사위를 _cursor 위치에 꽂는다
- 그래서 보관된 방어 주사위는 Ready 로 돌아와도 그 턴 안에 다시 잡히지 않고,
  ResetForNextTurn 이 _cursor = 0 과 함께 전부 Destroy 한다
- "방어 주사위를 들고 있다가 일방 공격당할 때 쓴다"는 설계가 배선까지 닿지 않은 상태로 보인다

■ DiceClashLog 가 보정 전 CurrentRoll 을 찍는다
- 합에서 검증할 때 로그 굴림값과 데미지가 어긋나 보인다.
  clashCtx.ModifiedRollA/B 로 바꾸거나 필드를 하나 더 두는 선택지
